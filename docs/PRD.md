## 1. 產品定位

**一句話定義**:一個三方角色(顧客 / 店家老闆 / 外送師)的**單店外送點餐系統**,顧客線上點餐、老闆備餐、外送師接單送達,並在完成後互相評分。

**現況本質**:目前不是「平台」而是「單一餐廳的外送工具」。因為:
- 沒有平台管理者(Admin)角色,沒人能審核店家或處理爭議
- 一位老闆只能開一家店(`OwnerController.SetupRestaurant` 檢查 `existing != null` 就擋掉)
- 外送費固定 30 元寫死在 `Order.DeliveryFee = 30` 與 `CartViewModel.DeliveryFee => 30`
- 金流是模擬的(`ConfirmPayment` 直接把狀態改成「已付款」)

專案名稱有兩套:方案名 `Yustore`、品牌名「YUYUEAT」、另有一個空殼專案 `AYuCantina`(scaffold 未使用)。

## 2. 使用者角色

| 角色 | Enum 值 | 進入點 | 核心任務 |
|---|---|---|---|
| 顧客 | `UserRole.顧客 = 0` | `/Customer/Index` | 找店 → 點餐 → 付款 → 追蹤 → 評分 |
| 外送師 | `UserRole.外送師 = 1` | `/Driver/Index` | 搶單 → 取餐 → 送達拍照 → 評分 |
| 老闆 | `UserRole.老闆 = 2` | `/Owner/Index` | 開店 → 管菜單 → 改訂單狀態 → 評分 |
| **管理員** | — | — | ❌ **完全不存在** |

角色在**註冊時由使用者自行勾選**(`RegisterViewModel.Role`),無任何審核。

### 3.6 結算(`Settlement`)

| ID | 需求 | 狀態 |
|---|---|---|
| S-1 | 外送師送達時自動產生一筆結算記錄(餐費歸老闆) | ✅ 寫入 |
| S-2 | 查看/執行結算 | ❌ **完全沒有任何讀取介面** |

商業模式推斷:**外送師向顧客收現金**(含餐費+外送費),外送費歸外送師,餐費須月底結算給老闆。這解釋了為何 `Settlement` 有 `DriverId`、`OwnerId`、`Year`、`Month`。但目前 Settlement 是「一訂單一列」,與月結語意矛盾。

## 4. 核心流程

### 4.1 訂單狀態機(現況)

```
待付款(0) ──顧客按付款──> 已付款(1) ──老闆──> 備餐中(2) ──老闆──> 待取餐(3)
                                                                      │
                                                            外送師搶單 ▼
                                          完成(6) <──有人評分── 已送達(5) <──送達拍照── 外送中(4)

已取消(7):狀態存在,但沒有任何程式碼會設定它
```

**現況問題**:`OwnerController.UpdateOrderStatus` 接受任意 `OrderStatus`,老闆可把「待付款」直接改成「完成」。狀態機只存在於 UI 想像中,後端無約束。

### 4.2 金流(現況)

```
顧客下單 → 假付款頁 → 按鈕 → Status=已付款  (沒有任何錢移動)
外送師送達 → 建立 Settlement(未結算) → 沒有任何後續
```

## 6. 明確的產品缺口(依優先度)

1. **沒有真實金流** — 假付款讓整個商業模式無法驗證
2. **沒有 Admin 後台** — 無人可審核店家/外送師、處理客訴、退款
3. **沒有取消/退款流程** — 顧客下錯單無解
4. **沒有結算功能出口** — 資料只寫不讀
5. **沒有即時性** — 狀態變更全靠重新整理頁面
6. **沒有多店/多分類/分頁** — 撐不起「平台」規模
7. **沒有忘記密碼** — 使用者忘記密碼即帳號報廢
8. **沒有通知系統** — 只有 Email,且只在一個時機點寄
